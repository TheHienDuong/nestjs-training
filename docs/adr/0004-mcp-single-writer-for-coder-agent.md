# ADR-0004: Claude Code is the single writer for Linear/Notion/Slack; Coder agent only receives SPEC.md

- **Status:** Accepted
- **Date:** 2026-08-11
- **Decision maker:** Hien Duong

## Context

The project splits responsibilities into two roles: Claude Code permanently holds the Mentor·PM·Reviewer role; the **Coder** role is flexible, primarily using **codex**, occasionally replaced or supplemented by other tools (**opencode**, or opencode running the DeepSeek model via the `opencode-go` provider...). All these CLI agents support self-configuring MCP servers (Linear, Notion, Slack...) exactly the same way Claude Code currently does.

If each agent independently connects to Linear/Notion/Slack to both read **and write**, the risks are real: two agents could simultaneously change the status of the same issue, Slack would receive duplicate notifications from multiple sources, and Notion notes could be overwritten by one agent after another. This is exactly the "multiple sources of truth" problem that [ADR-0002](0002-linear-as-source-of-truth.md) avoided by selecting Linear as the single source of truth — but ADR-0002 did not address the scenario of multiple _agents_, only multiple _systems_.

## Decision

1. **Only Claude Code maintains MCP connections to Linear, Notion, Slack, and Postman.** Any tool acting in the Coder role must not be configured with these MCP servers — this is unnecessary, as it does not fulfill the PM role.
2. Specifications for the Coder role are delivered via a **static file**: `docs/lessons/XX-ten-lesson/SPEC.md`, which is generated by Claude Code at the `/lesson-start` step by directly copying the original description of the corresponding Linear issue.3. The Coder agent only reads `SPEC.md` + `AGENTS.md` before starting work — **it does not query Linear on its own**.
4. `SPEC.md` is a point-in-time snapshot (serving the same role as `ROADMAP.md` for Linear per ADR-0002), **not the source of truth**. If a Linear issue is modified after `SPEC.md` is created, Claude Code will update the file when it detects a discrepancy — no other agent is allowed to edit `SPEC.md`.
5. The Coder role is **flexible per tool**, not a fixed list: each tool that fills this role uses its own dedicated branch named after the tool itself (`codex/...`, `opencode/...`, etc.) so that the comparison log (`docs/lessons/_agent-log.md`) can distinguish which tool/model a given solution originates from — no separate rule is required for each new tool.

## Considered Options

| Option | Pros | Cons | Reason for not being selected |
|--------|------|------|--------------------------------|| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| **Single-writer + SPEC.md** _(selected)_            | No write conflicts can occur; onboarding a new agent only requires teaching it to read `SPEC.md`, no additional tokens need to be issued | Requires a manual step: Claude must create/update `SPEC.md`                                                              | —                                                                             |
| All agents connect to full MCP                         | The coder agent can automatically fetch the latest issue, with no discrepancy                                                              | Real write race conditions; credentials must be issued and managed for each agent, increasing the attack surface                    | Trades a small convenience (no need to copy files) for a large risk (state conflicts) || Share a read-only Linear token with the coder agent | Direct read, no intermediate files needed | Linear's MCP OAuth does not offer a read-only scope at the tool-level permission tier; separate configuration is still required for each agent | Does not reduce configuration work, and there is still a risk of incorrect writes |
| --- | --- | --- | --- |
| Manually paste the spec into the prompt every time the agent is called | No files needed, no conventions required | Easy to copy incompletely, no record kept, cannot be reused across agent calls within the same lesson | Not sustainable, not auditable |

## Consequences

**Positive**

- No conflicting write sources to Linear/Notion/Slack — aligns with the spirit of ADR-0002 to extend to multiple agents.
- Adding a new coder agent (6th agent, 7th agent, etc.) requires no additional permission requests — it only needs to be able to read text files and `AGENTS.md`.
- `SPEC.md` is a fixed artifact in Git, so the **agent log** (`docs/lessons/_agent-log.md`) enables fair comparison: all agents receive the exact same spec at the exact same point in time.

**Negative / Costs**

- If Claude Code forgets to update `SPEC.md` after a Linear issue is modified, the coder agent will follow the old spec. The risk is low because lessons rarely change their objectives midway.- Adding one more file per lesson is acceptable, with the same cost as the existing `README.md`.

**Next steps**

- Update the `/lesson-start` skill to generate `SPEC.md` during the scaffold step.
- Update `AGENTS.md` and `docs/workflow/AGENT-MODEL.md` so that any agent reading them will correctly understand these boundaries.
