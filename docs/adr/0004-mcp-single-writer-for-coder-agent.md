# ADR-0004: Claude Code is the single writer for Linear/Notion/Slack; coder agents only receive SPEC.md

- **Status:** Accepted
- **Date:** 2026-08-11
- **Decision maker:** Hien Duong

## Context

The project splits two roles: Claude Code holds the fixed roles of Mentor·PM·Reviewer; the **Coder** role is flexible, primarily **codex**, occasionally replaced/augmented by other tools (**opencode**, or opencode running the DeepSeek model via the `opencode-go` provider...). All these CLI agents support self-configuring MCP servers (Linear, Notion, Slack...) exactly the same way Claude Code currently does.

If each agent independently connects to Linear/Notion/Slack to **read and write**, the risks are real: two agents simultaneously changing the status of the same issue, Slack receiving duplicate notifications from multiple sources, Notion notes being overwritten by one agent and overwriting another. This is exactly the "multiple sources of truth" problem that [ADR-0002](0002-linear-lam-nguon-su-that.md) avoided by selecting Linear as the single source of truth — but ADR-0002 only addressed multiple _systems_, not multiple _agents_.

## Decision

1. **Only Claude Code maintains MCP connections to Linear, Notion, Slack, Postman.** Any tool serving as the Coder is not allowed to configure these MCP servers — this is unnecessary, as it does not act as a PM.
2. Specifications for the Coder role are delivered via a **static file**: `docs/lessons/XX-ten-lesson/SPEC.md`, generated by Claude Code at the `/lesson-start` step by copying the full description of the corresponding Linear issue.
3. Coder agents only read `SPEC.md` + `AGENTS.md` before starting work — **they do not query Linear on their own**.
4. `SPEC.md` is a snapshot at a single point in time (similar to the role of `ROADMAP.md` for Linear per ADR-0002), **it is not the source of truth**. If a Linear issue is updated after `SPEC.md` is created, Claude Code updates the file when it detects a discrepancy — no other agent is allowed to modify `SPEC.md`.
5. The Coder role is **tool-flexible**, not a fixed list: each tool filling this role uses its own branch named after the tool itself (`codex/...`, `opencode/...`, etc.) so that the comparison log (`docs/lessons/_agent-log.md`) can distinguish which tool/model provided the solution — no separate rules are needed for each new tool.

## Considered Alternatives

| Alternative                                          | Pros                                                                                                              | Cons                                                                                                             | Reason for rejection                                                             |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| **Single-writer + SPEC.md** _(selected)_            | No risk of overlapping writes; onboarding a new agent only requires teaching it to read `SPEC.md`, no additional tokens need to be provisioned | There is a manual step: Claude must create/update `SPEC.md`                                                              | —                                                                             |
| All agents connect to full MCP                         | Coder agents can directly query the latest issues with no drift                                                              | Real race conditions when writing; credentials must be provisioned and managed for each agent, increasing the attack surface                    | We trade a small convenience (no need to copy files) for a large risk (state conflicts) |
| Share a read-only Linear token with the coder agent | Direct reading, no intermediate file needed                                                                        | Linear's MCP OAuth does not support a "read-only" scope at the per-tool permission level; separate configuration is still required for each agent | It does not reduce configuration work, and there is still a risk of accidental writes                        |
| Manually paste specs into the prompt every time the agent is called          | No file needed, no conventions required                                                                               | Easy to copy incorrectly, no record is kept, cannot be reused between multiple agent calls within the same lesson                 | Not durable, not auditable                                                   |

## Consequences

**Positive**

- No conflicting writes to Linear/Notion/Slack — aligns with the spirit of ADR-0002 extended to multiple agents.
- Adding a new coder agent (6th, 7th agent...) does not require requesting additional permissions — it only needs to be able to read text files and `AGENTS.md`.
- `SPEC.md` is a fixed artifact in Git, so the **agent log** (`docs/lessons/_agent-log.md`) enables fair comparison: all agents receive exactly the same spec at exactly the same point in time.

**Negative / Costs**

- If Claude Code forgets to update `SPEC.md` after a Linear issue is changed, the coder agent will follow the old spec. The risk is low because lessons rarely change their mid-term goals.
- Adding one more file per lesson is acceptable, with the same cost as the existing `README.md`.

**Next steps**

- Update the `/lesson-start` skill to generate `SPEC.md` during the scaffold step.
- Update `AGENTS.md` and `docs/workflow/AGENT-MODEL.md` so that any agent reading them correctly understands this boundary.
