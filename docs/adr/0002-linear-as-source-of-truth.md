# ADR-0002: Linear is the source of truth for tasks, with native GitHub and Slack integrations

- **Status:** Accepted
- **Date:** 2026-08-10
- **Decision maker:** Hien Duong

## Context

This learning project needs a place to manage ~26 lessons with complete descriptions, organized by phase, with priorities and estimates. At the same time, the learner wants to become familiar with **the tools and processes that a real backend team uses**, rather than a TODO file.

There are 4 systems involved: PM tool, GitHub (code + CI), Slack (notifications), and Notion (knowledge base). The greatest risk when using multiple systems is **information becoming inconsistent** — a task says "in progress" while the PR was merged last week.

## Decision

1. **Linear is the sole source of truth for task status.** No other system is considered authoritative for whether "this lesson is complete".
2. Enable Linear's native **GitHub integration** and **Slack integration**. Task status changes **because of git events**, not because someone clicks manually:
   - Create a branch using the name generated by Linear → the issue automatically moves to _In Progress_
   - A PR containing `Fixes NES-XX` is merged → the issue automatically moves to _Done_
3. Agents only automate what the integrations **cannot** do: write lesson notes, consolidate the Notion hub, and send learning digests.
4. `docs/ROADMAP.md` is a projection for offline reading, **not** the source of truth.

## Options considered

| Option                                     | Advantages                                                                                                                                                                                        | Disadvantages                                                                                                      | Why it was not chosen                                |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| **Linear + native integration** _(chosen)_ | The Initiative→Project→Issue→Sub-issue model fully represents the curriculum; cycles show actual velocity; the official MCP lets agents create/update tasks; GitHub/Slack integrations are native | Adds another account; the free tier has limits                                                                     | —                                                    |
| **GitHub Issues + Projects v2**            | Requires no external tool; closest to PRs                                                                                                                                                         | Lacks standard cycles/estimates; does not provide experience with a separate PM tool — something every company has | Loses part of the learning objective                 |
| **Trello**                                 | Visual and easy to start                                                                                                                                                                          | No automatic transition from PRs; no branch convention; shallow integration                                        | Would require manual updates → certain inconsistency |
| **Notion database as PM**                  | Combines tasks and knowledge in one place                                                                                                                                                         | No true git integration; Notion is strong for documentation, not issue tracking                                    | Use Notion for its strength: knowledge base          |

## Consequences

**Positive**

- There is no manual "update task" step → statuses cannot become inconsistent. This is exactly why real teams invest in integrations instead of relying on the discipline of manual updates.
- Develop an important habit: **branch names and PR descriptions are data, not decorative text**. When written correctly, the entire system runs automatically.
- Obtain real personal metrics: how many points are completed in each cycle and how far estimates differ.

**Trade-offs**

- Depends on naming branches correctly. An incorrect name → automation is lost, with no visible error → difficult to detect. This is documented clearly in [WORKFLOW.md](../workflow/WORKFLOW.md).
- Linear's free tier limits the number of open issues; if the limit is reached, create issues phase by phase instead of all at once.
- Four systems are a lot for one learner working alone. This is accepted because experiencing multiple systems at once is itself one of the objectives.

**Follow-up work**

- Enable the GitHub + Slack integrations in Linear Settings immediately after creating the repository and channel.
- The `/sync-progress` skill may only handle missing parts and **must not** update what the integrations have already handled — doing both would create two sources of truth, exactly what this ADR seeks to avoid.
