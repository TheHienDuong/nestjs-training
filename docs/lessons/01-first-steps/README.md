## 📚 Theory

### 1. The 5 files generated by `nest new`

```
src/
├── main.ts                 # entry point — bootstraps the application
├── app.module.ts           # root module — where everything is declared and wired together
├── app.controller.ts       # controller — receives HTTP requests
├── app.service.ts          # service — holds business logic
└── app.controller.spec.ts  # unit test for the controller
```

Official documentation describes them exactly as follows:

| File                     | Role                                                              |
| ------------------------ | ----------------------------------------------------------------- |
| `app.controller.ts`      | A basic controller with one route                                 |
| `app.controller.spec.ts` | Unit test for the controller                                      |
| `app.module.ts`          | Root module of the application                                    |
| `app.service.ts`         | A basic service with one method                                   |
| `main.ts`                | Entry file — uses `NestFactory` to create an application instance |

Right off the bat, note this: **the framework imposes structural separation on you from the very first file.** Express does not do this — with Express you have an empty `index.js` file and decide everything yourself. That freedom sounds nice, but the cost is that every Express project is organized differently, and new developers have to learn the structure from scratch every time.

> 📖 Source: [/first-steps](https://docs.nestjs.com/first-steps)

### 2. `main.ts` — the entry point

```ts
// src/main.ts
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  await app.listen(process.env.PORT ?? 3000);
}
void bootstrap();
```

Line by line:

- **`NestFactory.create(AppModule)`** — takes the **root module** as input and returns an object that implements the `INestApplication` interface. Under the hood, Nest scans the entire module tree starting from `AppModule`, reads metadata from decorators, initializes all providers, and **wires dependencies** between them. This is the **IoC container** at work.
- **Why `async`?** Because the initialization process may include asynchronous operations: connecting to a database, reading config from external sources, `useFactory` returning a Promise. Nest has to wait for all of these to finish before the application receives its first request.
- **`app.listen(port)`** — opens the HTTP listener. Only at this step does the application start accepting requests.
- **`void bootstrap()`** — `void` tells TypeScript that we intentionally do not `await` this Promise. See the explanation at [L00](../00-setup/README.md#a-small-but-noteworthy-change-in-src).

**A useful option to know:** by default, if an error occurs during application initialization, the app exits with exit code `1`. To make it **throw** the error instead of exiting (for example to handle it manually in tests):

```ts
const app = await NestFactory.create(AppModule, { abortOnError: false });
```

> 📖 Source: [/first-steps](https://docs.nestjs.com/first-steps)

### 3. Platform-agnostic — why Nest decouples from Express?

Nest is **not** an HTTP framework. It is an architectural layer **built on top of** an HTTP framework. Two platforms are supported out of the box:

| Platform           | Features                                                                                                                                   |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `platform-express` | Express — minimalist, battle-tested for years, large community, many libraries. **Default**, no action needed to enable.                   |
| `platform-fastify` | Fastify — high performance, low overhead, focused on speed. See [/techniques/performance](https://docs.nestjs.com/techniques/performance). |

This design choice exists so that **your application logic does not depend on the HTTP framework**. Your controllers, services, and modules know nothing about Express. Switching to Fastify is in principle just swapping the adapter, no need to rewrite business logic.

Normally you don't need to worry about the platform. You only need to declare a generic type when you want to access the underlying platform's API:

```ts
import { NestExpressApplication } from '@nestjs/platform-express';

const app = await NestFactory.create<NestExpressApplication>(AppModule);
// Now it is possible to call Express's own methods, for example app.set('trust proxy', 1)
```

> 🧠 **This is exactly hexagonal architecture** at the framework level. Express/Fastify are **adapters** for the "HTTP server" port; your application is the **core** that doesn't know which adapter is being used. You manually built this pattern in your Express project before — here Nest provides it out of the box.

> 📖 Source: [/first-steps](https://docs.nestjs.com/first-steps) · [/fundamentals/platform-agnosticism](https://docs.nestjs.com/fundamentals/platform-agnosticism)

### 4. How to run the application

| Command                          | What it does                                                          | Use case                        |
| -------------------------------- | --------------------------------------------------------------------- | ------------------------------- |
| `pnpm start`                     | Compile once and run                                                  | Quick checks                    |
| `pnpm start:dev`                 | `nest start --watch` — auto recompiles and restarts when files change | **Main dev loop**               |
| `pnpm start:debug`               | Same as above, with `--debug` to attach a debugger                    | Setting breakpoints             |
| `pnpm build` → `pnpm start:prod` | `nest build` outputs to `dist/`, then run `node dist/main`            | Matches production run workflow |

The docs have a useful tip: use the **SWC builder** for faster builds (docs claim up to ~20x faster):

```bash
pnpm start -- -b swc
```

SWC is a compiler written in Rust, much faster than `tsc`, but it **does not perform type checking** — it only transpiles code. This is a reasonable tradeoff for the dev loop, since you still get type checking from your IDE and from `pnpm build` in CI.

> 📖 Source: [/first-steps](https://docs.nestjs.com/first-steps) · [/recipes/swc](https://docs.nestjs.com/recipes/swc)

### 5. `app.module.ts` — root module

```ts
@Module({
  imports: [], // other modules required by this module
  controllers: [AppController], // controllers of this module
  providers: [AppService], // providers (services...) managed by the DI container
})
export class AppModule {}
```

`@Module` is just **metadata**. The `AppModule` class itself is empty. Nest reads this metadata on startup to know what to initialize and what to inject where.

Details are covered in L03 (Providers & DI) and L04 (Modules). For this lesson, just note: **this is where you declare "what exists in the application"**, separate from where you implement them.

### 6. Controllers and Services — why split them into two?

```ts
// app.controller.ts — only handles HTTP
@Controller()
export class AppController {
  constructor(private readonly appService: AppService) {}

  @Get()
  getHello(): string {
    return this.appService.getHello();
  }
}
```

```ts
// app.service.ts — only handles business logic
@Injectable()
export class AppService {
  getHello(): string {
    return 'Hello World!';
  }
}
```

With a function that just returns `'Hello World!'`, this split seems pointless. But this is an **intentional convention**, and the reason becomes clear as the system scales:

- **Controller** answers the question _"where does this HTTP request map to, where do parameters come from, what status to return?"_
- **Service** answers the question _"what does this business logic actually do?"_ — and it **knows nothing about HTTP**. This means the same service can be used for an HTTP controller, a CLI command, a message queue consumer, or a cron job.

`constructor(private readonly appService: AppService)` is **constructor injection**. You never `new AppService()` anywhere — Nest sees the `AppService` type in the constructor, automatically finds the matching provider, and injects it. This is the biggest difference from Express, and the core topic of L03.

> 📖 Source: [/controllers](https://docs.nestjs.com/controllers) · [/providers](https://docs.nestjs.com/providers)

### 7. `app.controller.spec.ts` — pre-written test from the start

```ts
const app: TestingModule = await Test.createTestingModule({
  controllers: [AppController],
  providers: [AppService],
}).compile();

appController = app.get<AppController>(AppController);
```

Note: the test **also builds a DI container**, just smaller — it only includes what the test needs. This is a direct consequence of using DI: since the controller receives dependencies via its constructor, you can replace the real `AppService` with a mock without modifying a single line in the controller.

**This is the real answer to the question "what is DI for?"** — it's not to make code look "professional", but to **allow replacing external dependencies**, and testing is the clearest use case. Details in L16.

> 📖 Source: [/fundamentals/unit-testing](https://docs.nestjs.com/fundamentals/unit-testing)

## 🔗 Connecting to prior knowledge

| Express                                                    | NestJS                                            | What's the difference                                                                                                                                                             |
| ---------------------------------------------------------- | ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `const app = express()`                                    | `const app = await NestFactory.create(AppModule)` | Nest is **async** because it has to initialize the entire dependency tree; Express is synchronous because it doesn't manage anything for you                                      |
| `app.listen(3000)`                                         | `await app.listen(3000)`                          | Same purpose                                                                                                                                                                      |
| `app.get('/', handler)`                                    | `@Get()` in `@Controller()`                       | Express: routes are registered via **function calls** at runtime. Nest: routes are declared via **metadata** on classes, Nest reads the metadata and registers them automatically |
| Manual directory organization                              | `.module.ts` / `.controller.ts` / `.service.ts`   | Nest enforces structural separation → all Nest projects look the same, new developers can understand them immediately                                                             |
| `const svc = require('./service')`                         | `constructor(private readonly svc: Service)`      | Express: you manually fetch dependencies. Nest: dependencies are **provided to you** (Inversion of Control)                                                                       |
| Switching Express → Fastify = rewrite the entire app       | Switching platform = swap the adapter             | Nest separates logic from the HTTP framework by design                                                                                                                            |
| Tests require `jest.mock('./service')` at the module level | `Test.createTestingModule({ providers: [mock] })` | Replace dependencies at the container level, no need to hack the module loader                                                                                                    |

**Food for thought:** in your Express + hexagonal architecture project, you have to manually "wire" dependencies at the entry point — you create repository instances yourself, pass them to use cases, pass use cases to handlers. `NestFactory.create(AppModule)` does **exactly this work**, but reads metadata from decorators to know what to wire to what. You already understand _why_ you need to wire dependencies; here we only change _how_ you wire them.

1. **`pnpm start:dev` + edit `app.service.ts` + curl:** ran `pnpm start:dev`, the bootstrap log printed the full route map (`AppController {/}` -> `Mapped {/, GET} route`, plus `UsersModule`/`TasksModule` routes). Changed `getHello()` to return `'Hello World! (L01 hands-on check)'` - the watcher auto-recompiled in ~3s (re-printing `InstanceLoader`/`RoutesResolver` logs in full), and `curl localhost:3000` immediately returned the new string. Reverted to `'Hello World!'`, curl confirmed the revert took effect.
2. **`pnpm build` + `pnpm start:prod`:** `nest build` generated `dist/` (`main.js`, `app.module.js`, `app.controller.js`, `app.service.js`, with `.d.ts`/`.js.map`, plus `tasks/` and `users/` folders). Opening `dist/app.service.js`: the `@Injectable()` decorator becomes `__decorate([(0, common_1.Injectable)()], AppService)` - proof that decorators are just **syntax for the compiler to call a metadata-attaching function**; plain JS has no runtime decorator concept. `node dist/main` (equivalent to `pnpm start:prod`) ran, `curl localhost:3000` returned `Hello World!`.
3. **`PORT=4000`:** `PORT=4000 node dist/main`, `curl localhost:4000` returned `Hello World!`; `curl localhost:3000` at that point got connection refused (nothing listening on port 3000) - confirming that `process.env.PORT ?? 3000` in `main.ts` works as expected.
4. **`pnpm start -- -b swc`:** ran successfully, the app bootstrapped and mapped routes normally, **no error**. However, checking `node_modules/@swc` shows it **does not exist**, and `@swc/core`/`@swc/cli` are **not in `devDependencies`** of `package.json` (they only appear in `pnpm-lock.yaml` as an optional peer dependency of `@nestjs/cli`, never installed). Honest conclusion: the `-b swc` flag is accepted by the CLI but **no SWC package is actually installed in this repo**, so there is no way to measure "faster than tsc" here - this is a real gap worth knowing, not a mistake on your part. We did not add `@swc/core`/`@swc/cli` to `package.json` here since changing dependencies is out of scope for this exception; to actually use SWC, install it deliberately and re-test.
5. **`NestExpressApplication` generic:** changed `NestFactory.create(AppModule)` to `NestFactory.create<NestExpressApplication>(AppModule)` (added `import { NestExpressApplication } from '@nestjs/platform-express'`). `pnpm build` compiled cleanly (0 errors), `node dist/main` ran, `curl localhost:3000` returned `Hello World!` exactly as before. Reverted to the original after confirming. **Why it doesn't change behavior:** the generic type only tells **TypeScript at compile time** that `app` has the full `INestApplication` interface **plus** the Express adapter's own methods (`app.set(...)`, `app.engine(...)`...) - it changes no value or logic at runtime, because `platform-express` is always the default adapter regardless of the generic. The generic only unlocks **type-checking**, not new **behavior**.
6. **Intentionally breaking DI:** removed `AppService` from `AppModule`'s `providers: []` (keeping the constructor injection in `AppController` unchanged), ran the app directly via `ts-node`. Nest printed exactly this real error:

   ```
   [Nest] ERROR [ExceptionHandler] UnknownDependenciesException [Error]: Nest can't resolve
   dependencies of the AppController (?). Please make sure that the argument AppService at
   index [0] is available in the AppModule module.

   Potential solutions:
   - Is AppModule a valid NestJS module?
   - If AppService is a provider, is it part of the current AppModule?
   - If AppService is exported from a separate @Module, is that module imported within AppModule?
   ```

   Read carefully: Nest knows **exactly** which class is missing (`AppService`), **where** (constructor of `AppController`, parameter index 0), and **which module** is missing it (`AppModule`) - because when building the dependency graph, Nest reads the constructor parameter's type via `reflect-metadata`, looks up that token in the module's `providers`, and if not found, throws `UnknownDependenciesException` right at bootstrap (fail-fast), not waiting for a real request. Restored `providers: [AppService]` after confirming the error.

**Where are you stuck, how to fix it:** Step 4 (SWC) initially looked like an environment issue - it turned out to be simply a missing package, not a misconfiguration. Lesson: `-b swc` does not surface a clear error when the package is missing - you have to check `node_modules`/`package.json` yourself to know which compiler is actually running.

## ✅ Review & Quiz

> The answers below are Hermes/Claude Code execution-substitute evidence (see the disclaimer at the top of this file), based directly on the real results in the Hands-on section.

1. **Why is `NestFactory.create()` `async` while `express()` is not?**
   → `express()` just creates an empty object, doing nothing asynchronous. `NestFactory.create()` has to scan the entire module tree starting from `AppModule`, read decorator metadata, and **initialize every provider** - a step that can include genuinely asynchronous work (a factory provider returning a `Promise`, opening a DB connection...). Nest must `await` the entire dependency graph before it can return an `app` ready to `listen()`.

2. **If your app never uses Express-specific APIs, what practical benefit does Nest's "platform-agnostic" nature bring?**
   → None of the `controllers/services/modules` import anything from `express`, so switching to `platform-fastify` (if higher performance is needed) is just a one-line change in `main.ts`, not a business-logic rewrite. Even without switching platforms, there's still a benefit: testing is easier (no need to mock real Express `req`/`res`), and the code doesn't accidentally leak HTTP-framework implementation details into the business layer.

3. **In hands-on step 6, what error does Nest report and what exactly does that message tell you?**
   → `UnknownDependenciesException`: "Nest can't resolve dependencies of the AppController (?). Please make sure that the argument AppService at index [0] is available in the AppModule module." The message tells you exactly 3 things: **which class** is missing (`AppService`), **where** (parameter index 0 in `AppController`'s constructor), and **which module needs the fix** (`AppModule`) - because Nest builds the dependency graph by reading the constructor parameter's type via `reflect-metadata`, and fails fast at bootstrap the moment it can't find a matching provider.

4. **`app.service.ts` only has a function that returns a string. If you put that string directly into the controller, what will break? Answer with a specific scenario that will happen later.**
   → Concrete scenario: when a cron job or a CLI command later also needs the "hello message" (without going through HTTP), that logic would have to be copy-pasted, because it's locked inside a controller method (only reachable via an HTTP request). If the logic lives in `AppService`, the cron job/CLI just injects the same service, no rewrite needed. This exact scenario already happened in the project's Task Management domain: `TasksService` (L02/L03) is used by `TasksController`, and in principle it is reusable by any other non-HTTP consumer.

5. **In `app.controller.spec.ts`, what problem does `Test.createTestingModule` solve that `jest.mock()` for Express-style code has to handle differently?**
   → `jest.mock('./service')` has to hack at the **module loader** level (replacing the entire module before the file importing it even runs) - this ties tightly to Node's `require`/ES module mechanism, and breaks easily when import paths are refactored. `Test.createTestingModule` replaces mocks at the **DI container** level: just declare `providers: [{ provide: AppService, useValue: mockService }]`, and Nest automatically puts the mock exactly where the controller needs it - without touching how files import each other, consistent with the exact mechanism `AppController` already uses to receive its dependency at real runtime.

## 🧠 Key Takeaways

1. `NestFactory.create(AppModule)` is `async` because it must fully build and initialize the entire dependency graph before the app is ready to accept requests.
2. Platform-agnostic means controllers/services/modules don't know whether Express or Fastify is running underneath; only `main.ts` touches the concrete platform (`NestExpressApplication`), and declaring that generic **does not change runtime behavior**, only unlocks type-checking.
3. Decorators (`@Injectable()`, `@Controller()`...) exist only at compile time - the generated JS uses `__decorate(...)` to call the metadata-attaching function; there is no such thing as a decorator at plain runtime.
4. Missing a provider in `providers: []` while still injecting it in a constructor -> Nest fails fast at bootstrap with `UnknownDependenciesException`, pinpointing the exact class/position/module - not a hard-to-trace runtime bug.
5. `-b swc` does not self-report an error when `@swc/core`/`@swc/cli` are missing - you must check `node_modules`/`package.json` yourself to know which compiler is actually running.
