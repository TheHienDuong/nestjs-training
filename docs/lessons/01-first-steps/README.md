## 📚 Theory
### 1. The 5 files generated by `nest new`
```
src/
├── main.ts                 # entry point — bootstraps the application
├── app.module.ts           # root module — where all components are declared and linked
├── app.controller.ts       # controller — handles incoming HTTP requests
├── app.service.ts          # service — contains business logic
└── app.controller.spec.ts  # unit test for the controller
```

Official documentation describes them as follows:

| File                     | Role                                                  |
| ------------------------ | -------------------------------------------------------- |
| `app.controller.ts`      | A basic controller with a single route                      |
| `app.controller.spec.ts` | Unit test for the controller                                 || `app.module.ts`          | Root module of the application                                 |
| `app.service.ts`         | A basic service with a single method                        |
| `main.ts`                | Entry file — uses `NestFactory` to create an application instance |

The first thing that stands out: **the framework enforces a project structure on you right from the very first file.** Express doesn't work this way — with Express, you start with an empty `index.js` file and make all structural decisions yourself. That freedom sounds appealing, but the tradeoff is that every Express project is organized differently, and new developers have to learn the project structure from scratch.

> 📖 Source: [/first-steps](https://docs.nestjs.com/first-steps)

### 2. `main.ts` — entry point

```ts
// src/main.ts
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  await app.listen(process.env.PORT ?? 3000);
}
void bootstrap();
```

Line by line:

- **`NestFactory.create(AppModule)`** — accepts the **root module** as input and returns an object that implements the `INestApplication` interface. Internally, Nest scans the entire module tree starting from `AppModule`, reads metadata from decorators, initializes all providers, and wires up **dependency injection** between them. This is the **IoC container** at work.- **Why `async`?** Because the initialization process may include asynchronous operations: database connection, reading config from external sources, `useFactory` returning a Promise. Nest has to wait for all of these to complete before the application receives the first request.
- **`app.listen(port)`** — opens the HTTP listener. At this step, the application finally starts receiving requests.
- **`void bootstrap()`** — `void` tells TypeScript that we intentionally do not `await` this Promise. See the explanation at [L00](../00-setup/README.md#a-small-noteworthy-change-in-src).

**A notable option:** By default, if an error occurs during application initialization, the app exits with exit code `1`. To make it **throw** the error instead of exiting (for example, to handle it automatically in tests):

```ts
const app = await NestFactory.create(AppModule, { abortOnError: false });
```

> 📖 Source: [/first-steps](https://docs.nestjs.com/first-steps)

### 3. Platform-agnostic — why is Nest decoupled from Express?

Nest **is not** an HTTP framework. It is an architectural layer **built on top of** an HTTP framework. Two platforms are supported out of the box:

| Platform           | Features                                                                                                                                     |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- || `platform-express` | Express — minimalist, battle-tested over years of production use, large community, extensive library support. **Enabled by default**, no action required to activate it. |
| `platform-fastify` | Fastify — high performance, low overhead, focused on speed. See [/techniques/performance](https://docs.nestjs.com/techniques/performance). |

Why this design? To ensure **your application logic is not tied to the HTTP framework**. Your controllers, services, and modules have no awareness of Express. Switching to Fastify is simply a matter of changing the adapter, with no need to rewrite your business logic.

In most cases you do not need to concern yourself with the platform. You only need to declare the generic type when you want to access the underlying platform's API:

```ts
import { NestExpressApplication } from '@nestjs/platform-express';

const app = await NestFactory.create<NestExpressApplication>(AppModule);
// now you can access Express-specific methods, e.g. app.set('trust proxy', 1)
```

> 🧠 **This is hexagonal architecture implemented at the framework level**. Express/Fastify serve as **adapters** for the "HTTP server" port; your application is the **core** that has no knowledge of which adapter is in use. You have likely built this pattern manually in your past Express projects — Nest provides this implementation out of the box here.

> 📖 Source: [/first-steps](https://docs.nestjs.com/first-steps) · [/fundamentals/platform-agnosticism](https://docs.nestjs.com/fundamentals/platform-agnosticism)

### 4. How to run the application| Command                             | What it does                                                        | Use when                   |
| -------------------------------- | ------------------------------------------------------------- | -------------------------- |
| `pnpm start`                     | Compiles then runs once                                      | Quick check             |
| `pnpm start:dev`                 | `nest start --watch` — automatically recompiles and restarts when files change | **Main dev loop**     |
| `pnpm start:debug`               | Same as above, with `--debug` to attach a debugger                    | Set breakpoints             |
| `pnpm build` → `pnpm start:prod` | `nest build` outputs to `dist/`, then runs `node dist/main`                 | Same as the production run method |

The documentation has a useful tip: use the **SWC builder** for faster builds (docs state up to ~20x faster):

```bash
pnpm start -- -b swc
```

SWC is a compiler written in Rust, much faster than `tsc` but **does not perform type checking** — it only transpiles code. This is a reasonable tradeoff for the dev loop, as you still get type checking from your IDE and from `pnpm build` in CI.

> 📖 Source: [/first-steps](https://docs.nestjs.com/first-steps) · [/recipes/swc](https://docs.nestjs.com/recipes/swc)

### 5. `app.module.ts` — root module

```ts
@Module({
  imports: [], // other modules required by this module
  controllers: [AppController], // controllers belonging to this module
``````ts
  providers: [AppService], // provider (service...) managed by the DI container
})
export class AppModule {}
```

`@Module` is just **metadata**. The `AppModule` class itself is empty. Nest reads this metadata on startup to know what to initialize and where to inject dependencies.

We dive deeper into this in L03 (Providers & DI) and L04 (Modules). For this lesson, just note: **this is where you declare "what exists in the application"**, separate from where they are implemented.

### 6. Controller and Service — why separate them?

```ts
// app.controller.ts — handles only HTTP
@Controller()
export class AppController {
  constructor(private readonly appService: AppService) {}

  @Get()
  getHello(): string {
    return this.appService.getHello();
  }
}
```

```ts
// app.service.ts — handles only business logic
@Injectable()
export class AppService {
  getHello(): string {
    return 'Hello World!';
  }
}
```

With a function that returns `'Hello World!'`, this separation seems pointless. But this is an **intentional convention**, and the reason becomes clear as the system scales:

- **Controller** answers the question _"where does this HTTP request map to, where are parameters retrieved from, what status code is returned?"_
- **Service** answers the question _"what does this business logic actually do?"_ — and it **knows nothing about HTTP**. This allows the same service to be used for an HTTP controller, a CLI command, a message queue consumer, or a cron job.`constructor(private readonly appService: AppService)` is **constructor injection**. You never `new AppService()` anywhere — Nest sees the `AppService` type in the constructor, automatically finds the matching provider and injects it. This is the biggest difference from Express, and is the core content of L03.

> 📖 Source: [/controllers](https://docs.nestjs.com/controllers) · [/providers](https://docs.nestjs.com/providers)

### 7. `app.controller.spec.ts` — pre-existing test

```ts
const app: TestingModule = await Test.createTestingModule({
  controllers: [AppController],
  providers: [AppService],
}).compile();

appController = app.get<AppController>(AppController);
```

Note: tests **also build a DI container**, just smaller — it only contains what the test requires. This is a direct consequence of using DI: since the controller receives dependencies via the constructor, you can replace the real `AppService` with a mock without modifying a single line in the controller.

**This is the real answer to the question "What is DI for?"** — it's not to make code look "professional", but to **be able to replace external dependencies**, and testing is the clearest use case. Details are in L16.

> 📖 Source: [/fundamentals/unit-testing](https://docs.nestjs.com/fundamentals/unit-testing)

## 🔗 Connection to prior knowledge| Express                                          | NestJS                                            | What's the difference?                                                                                                                              |
| ------------------------------------------------ | ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `const app = express()`                          | `const app = await NestFactory.create(AppModule)` | Nest is **async** because it must initialize the entire dependency tree; Express is synchronous because it does not manage anything for you                                                 |
| `app.listen(3000)`                               | `await app.listen(3000)`                          | Same meaning                                                                                                                        |
| `app.get('/', handler)`                          | `@Get()` trong `@Controller()`                    | Express: routes are registered via **function calls** at runtime. Nest: routes are declared using **metadata** on classes; Nest reads the metadata and registers them automatically. || You define the folder structure yourself | `.module.ts` / `.controller.ts` / `.service.ts` | Nest enforces layered architecture → every Nest project looks identical, new team members can get up to speed immediately |
| `const svc = require('./service')` | `constructor(private readonly svc: Service)` | Express: you manually retrieve dependencies. Nest: dependencies are **provided to you** (Inversion of Control) |
| Switching from Express to Fastify = rewriting the entire app | Switching platforms = swapping the adapter | Nest separates business logic from the HTTP framework from the ground up |
| Tests require `jest.mock('./service')` at the module layer | `Test.createTestingModule({ providers: [mock] })` | Replace dependencies at the container layer instead of hacking the module loader |

**Food for thought:** in your Express + hexagonal architecture project, you have to manually wire dependencies at the entry point — you manually instantiate repositories, pass them to use cases, and pass use cases to handlers. `NestFactory.create(AppModule)` does **exactly that**, but it reads metadata from decorators to know what to wire where.
