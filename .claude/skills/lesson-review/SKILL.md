# Lesson Review

Truly review the user's hands-on work like a real senior reviewer, and verify the user **understands** the material rather than just **can get it to run**.

## Why this skill is necessary

The biggest risk of learning with AI support is **false proficiency**: the code runs, tests pass, but the user can't rewrite it on their own. This skill adds a fixed checkpoint: you only count as complete if you can explain _why_ the solution works.

It also keeps review quality consistent. Casual, arbitrary reviews will grow more lenient over time, right when the code becomes more complex.

## Step 1 — Check what the user has done

```bash
git branch --show-current
git diff main...HEAD --stat
git diff main...HEAD
```

Read the **entire** diff before leaving any feedback. Also read the lesson note to understand what the hands-on requirements are.

## Step 2 — Run the automated check

```bash
pnpm lint
pnpm test
pnpm build
```

If there are errors, inform the user and **let them fix it themselves**, with directional hints. Do not fix it for them: debugging is the most valuable part of the learning process.

## Step 3 — Review like a senior

Follow the priority order: correctness first, cleanliness second.

### 3.1 Correctness

- Are there actual bugs? Edge cases like empty values, `null`, non-existent IDs?
- Are the HTTP status codes semantically correct? (`201` for create, `204` for delete with no response body, `404` when not found)
- Are errors being swallowed? Are all `async` operations properly `await`ed?

### 3.2 Idiomatic NestJS

- Is business logic placed in **services**, with controllers only handling HTTP? This is the most common mistake for people migrating from Express.
- Are dependencies injected via **constructor injection**, not instantiated directly with `new`, and not imported as global singletons?
- Are providers declared and exported in the correct module?
- Are built-in utilities used instead of reinventing the wheel? (`NotFoundException` instead of `throw new Error`, `ParseIntPipe` instead of manual `parseInt`)
- Are decorators used at the correct scope (method / controller / global)?

### 3.3 Reusability

- Is there duplicate logic already present in `src/`? Search using the Serena MCP (`find_symbol`, `find_referencing_symbols`) before concluding it is new.
- Are you rewriting functionality that NestJS already provides out of the box?

### 3.4 Types and data boundaries

- Are there unnecessary uses of `any`? (The repo disables `no-explicit-any` so ESLint will not catch it — the reviewer needs to flag it)
- Are DTOs validated at the input boundary? Do responses leak sensitive fields (`password`, `refreshToken`)?

### 3.5 Tests

- Do tests verify **behavior** instead of just checking if mocks were called?
- Are there error cases, not just the happy path?

## Step 4 — Present feedback

Categorize by severity, and **always explain why**, not just list what needs to be fixed:

```
🔴 Phải sửa      — bug hoặc sai nguyên tắc NestJS
🟡 Nên sửa       — chạy được nhưng chưa idiomatic
🟢 Gợi ý         — tuỳ chọn, để biết thêm
👍 Làm tốt       — nêu cụ thể, không khen chung chung
```

For every 🔴 and 🟡: point to file:line, explain the reason, and include a link to documentation. **Do not write the fix code immediately** — describe the direction and let the user fix it themselves. Only provide sample code if the user still can't get it right after two attempts.

Praise should be specific. "Great code" teaches nothing; "Extracting `findOwnedProject` out of `update` was the right call, since this method will be reused in `delete`" is useful feedback.

## Step 5 — Quiz (mandatory)

Take the questions from the **✅ Review & Quiz** section in the lesson note (generated by `/teach`) and ask the user. Add 1–2 questions closely tied to the code the user just wrote:

> _"In `TasksController.findOne`, you used `ParseIntPipe`. What happens if a client calls `/tasks/abc`, what status code is returned, and who generates that response?"_

Grading:

- Answers in their own words → ✅
- Answers correctly but sounds like they're reading from docs → ask a follow-up "what if..." question to verify real understanding
- Can't answer → **the lesson is not Done**. Go back to the relevant theory section, re-explain it in a different way, then ask again.

Add one **prior knowledge review** question: connect this lesson to a previous lesson, or to Express/Prisma/hexagonal.

## Step 6 — Record in the lesson note

Fill out `docs/lessons/XX-*/README.md`:

- **✅ Review & Quiz** section: the user's answers (verbatim, even if imperfect — they'll see their progress when reading it back later)
- **🧠 Key takeaways** section: maximum 5 lines
- **Things I used to misunderstand** section: if the quiz reveals any misconceptions

## Step 7 — Finalize

Clearly state whether the lesson has met the **Definition of Done** (5 criteria in `docs/workflow/WORKFLOW.md`). If it has, guide them to open a PR:

```bash
git push -u origin $(git branch --show-current)
gh pr create --fill   # remember to include the line "Fixes NES-XX" in the description
```

## Boundaries

- **Do not** modify the user's hands-on code yourself.
- **Do not** pass the lesson if the quiz is not passed, even if the code is perfect.
- **Do not** commit or push on the user's behalf.
- Be strict but not tricky. The goal is for the user to understand, not to make them feel inadequate.
