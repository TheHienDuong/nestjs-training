# lesson-start

Start a new lesson using the correct process so every lesson is consistent and no step is ever omitted.

## Why this skill is needed

This is repeated 26 times. Doing it manually causes drift: lesson 3 uses one branch naming style, lesson 12 another, and notes omit the "Connections to prior knowledge" section — even though it is the most important section. In particular, the branch name **must** match the Linear convention or all task-status automation is lost (see `docs/adr/0002-linear-as-source-of-truth.md`).

## Input

A lesson code (`L02`) or name (`controllers`). If none is provided → use the first ⬜ lesson in `docs/ROADMAP.md`.

## Steps

### 1. Identify the lesson

Read `docs/ROADMAP.md` and find the lesson row. Get its number, name, phase, and documentation links. If it is already ✅ → ask whether the user wants to repeat it.

### 2. Check the current working state

```bash
git status --short && git branch --show-current
```

- Uncommitted changes exist → **stop**, inform the user, and do not stash automatically.
- Currently on another unmerged lesson branch → ask before leaving it.

### 3. Retrieve the Linear issue

Use Linear MCP to find the lesson issue in the corresponding project.

- **Issue exists:** get `identifier` (e.g. `NES-12`), `branchName` (generated by Linear — use this exact string), and the description.
- **No issue exists:** create one using the structure in _Issue description format_ below and assign the correct project + label `phase-X`.
- **Linear MCP is not connected:** tell the user to run `! claude mcp add --transport http linear https://mcp.linear.app/mcp` and then `/mcp`. Continue the remaining steps using a branch in the form `lesson/XX-lesson-name`, and record that the Linear linking step is still pending.

### 4. Create the branch

```bash
git checkout main && git pull origin main
git checkout -b <branchName from Linear>
```

The branch name **must** be copied exactly from Linear's `branchName` field. Do not invent one — the embedded `nes-XX` string is what Linear uses for identification.

### 5. Scaffold the lesson note

Copy `docs/templates/lesson-note.md` → `docs/lessons/XX-lesson-name/README.md`.

Pre-fill the title, metadata table (phase, Linear ID, branch, docs, today's date), and the **🎯 Objectives** section from the issue description. **Leave** Theory / Hands-on / Quiz **blank** — they are completed during `/teach` and `/lesson-review`.

### 6. Move the issue to In Progress

Update the issue state through Linear MCP. (If the GitHub integration is enabled, step 4 also does this automatically — updating it again is harmless because the value is the same.)

### 7. Report to the user

Reply concisely in English:

- Which lesson, which branch, and where the note is
- Lesson objectives (3–5 bullets)
- The next command to enter: `/teach <topic>`

## Linear issue description format

```markdown
## 🎯 Learning objectives

- <3–5 measurable bullets>

## 📚 Official documentation

- [<section name>](<full docs.nestjs.com link>)

## 🔗 Connections to prior knowledge

- Express/Prisma/hexagonal: <comparison>

## 🛠 Hands-on

<what code, in which file, and how to verify it>

## ✅ Definition of Done

- [ ] Lesson note includes Connections to prior knowledge + Sources
- [ ] Hands-on work runs
- [ ] Test pass
- [ ] Pass the quiz during review
- [ ] PR has passing CI and is merged
```

## Boundaries

- **Do not** write `src/` code — this step opens the lesson; it is not the implementation step.
- **Do not** commit anything. Only create the branch and note file.
- **Do not** rename Linear's branch to make it "prettier".
