**NestJS learning project**, not a commercial product. The user (Hien Duong) is a **beginner backend developer** who already knows Node.js, Express, Prisma and basic hexagonal architecture, and is currently learning NestJS 11 using the official documentation at `docs.nestjs.com`.

## Documentation rules — important

`docs.nestjs.com` is an **Angular SPA**: `WebFetch` only returns the title tag, no content. Get the original markdown from the official upstream repository:

```bash
gh api "repos/nestjs/docs.nestjs.com/contents/content/controllers.md" \
  -H "Accept: application/vnd.github.raw"
```

**Do not teach NestJS from memory.** The model's knowledge cutoff may be older than the version in `package.json`. To get a library version, run `npm view <pkg> version`, do not guess.

Some file names differ from URLs: `/middleware` → `middlewares.md`; `/fundamentals/custom-providers` → `fundamentals/dependency-injection.md`; `/fundamentals/injection-scopes` → `fundamentals/provider-scopes.md`; `/techniques/database` → `techniques/sql.md`; `/faq/common-errors` → `faq/errors.md`.

## Package manager

**pnpm** (lockfile `pnpm-lock.yaml`). Do not use npm or yarn.

## Common commands

```bash
pnpm install
pnpm start:dev                 # watch mode — main dev loop
pnpm lint                      # eslint --fix
pnpm format                    # prettier --write
pnpm test                      # unit test
pnpm test -- app.controller    # one file
pnpm test -- -t "tên test"     # by test name
pnpm test:e2e                  # e2e
pnpm verify                        # exactly what CI runs: lint + format + test + build
pnpm db:up / db:down           # postgres + redis via docker compose
```

Run `pnpm verify` before opening a PR so you don't have to wait for CI to see failures.

## Architecture & conventions

- Standard Nest layer separation: `*.module.ts` ties together providers/controllers · `*.controller.ts` handles only HTTP · `*.service.ts` holds business logic. **Business logic must not be placed in controllers** — this is the most common mistake for developers migrating from Express.
- Unit tests `*.spec.ts` are placed next to the source file (`rootDir: src`). E2E tests are in `test/*.e2e-spec.ts` using `test/jest-e2e.json`.
- `tsconfig.json`: `nodenext`, `strictNullChecks: true`, `noImplicitAny: false` (full `strict` mode is not enabled yet).
- ESLint uses `typescript-eslint` `recommendedTypeChecked` + `eslint-plugin-prettier`. `no-explicit-any` is **disabled** → ESLint will not catch `any` usage, reviewers must catch it. `no-floating-promises` and `no-unsafe-argument` are set to `warn`, but **CI runs with `--max-warnings=0`** so warnings also cause CI to fail.
- Prettier is the single source of truth for formatting `.ts`, `.json`, `.md`, `.yml` files. Check `.prettierignore` for exceptions.

## Quality gates

| Quality gate                            | Location                                     |
| --------------------------------------- | --------------------------------------------- |
| `lint-staged`                           | git hook `pre-commit`                         |
| `commitlint` (Conventional Commits)      | git hook `commit-msg`                         |
| CI: lint + format + test + build         | GitHub Actions                                |
| Branch protection for `main`             | GitHub — direct push is forbidden, CI must pass |

Commits with incorrect format are **blocked locally**. Never suggest using `--no-verify` to take shortcuts — this gate is part of the learning process.

## Git

- Branch names must **exactly match** the name generated by Linear (`hien/nes-XX-...`). The `nes-XX` string is what Linear uses to automatically update issue status.
- PR descriptions **must** include `Fixes NES-XX`.
- Merge using **Squash and merge**: 1 lesson = 1 commit on `main`.
- Remote: `origin` = GitHub (main working repository), `gitlab` = company repository. **Do not touch `gitlab`.**
