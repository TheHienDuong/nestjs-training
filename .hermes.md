## 3. Approval gateway — the strictest rule

1. **Never dispatch an agent without user approval.** Mandatory flow: Hermes proposes → user approves → only then does it run. Dispatch via a Herdr pane must also follow this exact flow — no exceptions.
2. Before dispatching, Hermes must announce in chat: agent, model, task, branch, workdir, limits (max-turns/budget), and how it will be verified.
3. Agents run on a **dedicated branch** (`codex/nes-XX-...`, `agy/nes-XX-...`) — never on main, never on your `hien/...` lesson branch.
4. Agents **must not**: push straight to main, merge, open a PR outside the approved flow, or edit files outside their scope.
5. Agent output only reaches main via a **dedicated PR** (ADR-0005): Claude Code **reviews it locally** → Codex GitHub App connector review (layer 1, automated, `chatgpt-codex-connector[bot]`) → lead review by the user → squash merge. **Copilot CLI does NOT run automatically** — it is only dispatched for large MRs (`mr/*`, max 2/day, see `docs/workflow/REVIEW-MODEL.md`).
6. No agent reviews its own code.
7. **Hermes does not merge — only the user (Hien Duong) finalizes merges.** Claude Code does not merge either.

## 5. Standard operating flow (per task)

1. User submits a request → Hermes classifies it per the routing table, proposes (agent + model + task + branch + limits).
2. User approves → Hermes dispatches **the exact command the user would run themselves** (no proxy wrapping, no model changes, no added layers — non-interference). The Herdr bridge (section below) is the second dispatch method; exec/print-mode is still used for small tasks that don't need approval.
3. The agent reads AGENTS.md + the SPEC before working; commits carry that tool's `Co-authored-by` trailer (see section 9).
4. When the agent finishes → Hermes **verifies independently**: git log/status, reads the full diff, runs `pnpm verify` — it does not trust the agent's self-report.
5. Hermes opens a PR (description must include `Fixes NES-XX`) → **mentions @TheHienDuong** → **Claude Code reviews it locally** → **Codex GitHub App connector review** (automated, code-quality layer, every PR) → the user is the final lead reviewer → **only the user merges** (with the mandatory approval of code owner `@hienduong-agilityio`). For large MRs (`mr/*`): add a **Copilot gatekeeper review** (dispatched via herdr, max 2/day) before the user merges.
6. Squash merge → Hermes reports a summary + logs one line to `docs/lessons/_agent-log.md` (only once the user reports the merge / Hermes is asked — never run in the background) → **mandatory cleanup** of the workspace/worktree/pane + local branch for that task (see "Mandatory cleanup" below) — do not wait for the user to ask.

## 6. Reporting & operations

- Hermes reports every milestone **in chat**: dispatch, running, done, verification results, PR link, resume command.
- After each round, Hermes reports back to the user: what was done, verification evidence, PR/link, proposed next step — **the user decides** (keep reviewing / merge / iterate).
- After opening a PR: mention the user + stop. **Never run in the background/as a daemon waiting for a merge.** Multiple PRs → report a single "needs your review" list.
- Do not create a separate dispatch script/daemon/registry (`~/.hermes/agents/` was removed on 2026-08-11) — chat is the live feed itself. Task state uses native `hermes kanban` + the `herdr-agent-state` plugin; do not hand-roll a separate registry.

## Mandatory cleanup — workspace/worktree/pane/branch after a task is done

> Mandatory, not optional. Applies to every task dispatched via Herdr (a dedicated worktree for the Coder/agy). Immediately after a task/PR is **fully done** (squash-merged into main) or **explicitly abandoned** (user reports dropping the task, closes the PR without merging, closes the issue), Hermes must clean up the Herdr workspace/worktree/pane used for that task and delete the corresponding local branch — never leave a useless worktree taking up space.

**When to run — immediately, without being reminded:**

- Right after the user reports the PR has been squash-merged (or Hermes independently verifies the branch is already in `main`'s history).
- Right after the user reports abandoning/dropping the task (closing the Linear issue, closing the PR without merging, changing direction).

**Resolve the target dynamically — mandatory before deleting anything (never trust a stale label/id):**

1. `herdr agent list` — get the current list of workspaces/worktrees/panes; never reuse an id/label recorded at dispatch time (pane/workspace drift has actually happened — see the guardrail below).
2. `git status` in the exact worktree — confirm there are no uncommitted changes.
3. Check PR state (`gh pr view <branch> --json state,mergedAt`) and the Linear issue state before deleting the branch — the branch must already be merged or the PR must be definitively closed.

**Safety exceptions — NEVER delete when any of the following applies:**

- The `main` worktree or the user's current worktree (open/in use for work).
- A lesson/coder/reviewer worktree that is still **active** (task not closed, in local review or waiting on CI/PR).
- A worktree with **uncommitted changes** (`git status` not clean) — never delete unsaved work.
- A branch with an **open PR** (not merged, not closed).
- A pane that is **busy** or still needed for something else (agent hasn't finished its turn, user is watching/interacting).

**Remote branches:** by default, do **not** delete the branch on `origin` — only delete the **local branch** (`git branch -D`). Only delete a remote branch when the user **explicitly and separately** requests it for that instance.

**If blocked:** report the exact blocking reason in chat (e.g. "worktree X still has uncommitted changes", "PR #NN is still open", "pane Y is still running an agent") — never force the deletion, never silently skip the cleanup step. Retry the cleanup as soon as the blocking condition is resolved (PR merged/closed, agent finished, user committed or discarded changes).

**Cleanup commands (run only after all the checks above pass):**

```bash
herdr worktree remove --workspace <id> --force
git branch -D <branch>
```

## Herdr bridge (PTY-pane dispatch)

> Approved by the user on 2026-08-14 (ADR-0006). A second dispatch method alongside exec/print-mode (§5.1).

**Principle:** the pane is for the HUMAN to see & intervene; the filesystem is for the MACHINE to know when it's done.

**9-step flow:**

1. `hermes kanban create/claim` — task state (the single source of truth)
2. `herdr worktree create --cwd <repo> --branch codex/nes-XX-... --label NES-XX --json` — auto-creates a workspace + tab + pane, cwd = the worktree
3. `herdr agent start <name> --kind codex --pane <pane_id> --timeout 60000` — one ephemeral agent per task (avoids context pollution)
4. `herdr agent prompt <pane_id> "<task> + MUST write <worktree absolute path>/.hermes/runs/NES-XX.json (nonce, git rev-parse HEAD, result)"`
5. Hermes **polls the JSON file as the sole verdict**. `pane wait-output --match` with a string that appears in the prompt is FORBIDDEN (a proven false positive on 2026-08-14); `herdr agent wait` does not track turns → never used as the done verdict
6. Independent verify: RAW `git diff` + `pnpm verify` — does not trust the agent's self-report
7. Dedicated PR `Fixes NES-XX` + trailer → **Claude Code reviews it locally** → Codex GitHub App connector review (automated) → **user merges** (ADR-0005 unchanged); if later bundled into a large MR `mr/*`, add a Copilot gatekeeper review before "releasing" it (ADR-0008)
8. `hermes kanban complete`
9. **Mandatory cleanup** (see "Mandatory cleanup — workspace/worktree/pane/branch after a task is done" above) — not an optional step: dynamically resolve the target with `herdr agent list`, check `git status` + PR status, only then `herdr worktree remove --workspace <id> --force` + `git branch -D <branch>`. If a safety exception applies (uncommitted changes, open PR, busy pane), report a blocker — never force the deletion.

**Commands verified on 2026-08-14:** worktree create auto-creates workspace/tab/pane; `pane split --pane <id> --direction right --cwd <path>`; `agent start --kind codex` (interactive_ready); `agent prompt` sends successfully (do not trust `--wait` for done); `worktree remove --workspace <id> --force`; note `tab close` fails with "last tab" → use worktree remove / workspace close instead.

**Guardrails:**

- Resolve the target dynamically with `herdr agent list` before every dispatch — do not trust a stale label/pane id (pane drift has actually happened)
- Cap 2-3 worker panes at once — more than that and the human can't keep up with approvals
- Do not touch the pane Claude Code is currently running in (currently: w1:p1)
- `herdr agent read` is only for diagnosing when blocked/failed — never used to fetch the result
- Official profiles: **coder-codex** (Coder) · **mentor-claude** (Mentor/PM/Reviewer local) · **reviewer-copilot** (Gatekeeper for large MRs — `mr/*` only) · **coder-agy** (Counter-view, NOT wrapped — bare CLI) · **writer** (docs). `coder-fast`, `reviewer-gate`: archived — not used in the standard flow
- Dispatch via Herdr still must go through the approval gateway in §3 — no exceptions

## 8. Technical contract (inherited from AGENTS.md/CLAUDE.md)

- Package manager: **pnpm** only. Before opening a PR / reporting done: run `pnpm verify` (lint --max-warnings=0 + prettier check + test + build).
- Conventional Commits; commitlint blocks at the hook — **never** use `--no-verify`.
- Branch names must match the Linear-generated name (`hien/nes-XX-...`); PR must include `Fixes NES-XX`; squash merge; never push straight to main (ruleset `protect-main`).
- NestJS: business logic in the service, controller handles only HTTP, DI via constructor injection. `strictNullChecks` on, avoid `any`.
- Tests: `*.spec.ts` next to src, e2e in `test/`; test behavior + always include an error case.
- Documentation: `docs.nestjs.com` is an Angular SPA → get the raw markdown with `gh api repos/nestjs/docs.nestjs.com/contents/content/<file>.md`. Library version: `npm view <pkg> version`, never guess.
- Language: reply and write documentation in **Vietnamese**, keep English technical terms (provider, guard, interceptor, pipe, DI, decorator).
- Remotes: origin = GitHub (working remote), gitlab = company repo — **do not touch gitlab**.
- **Bilingual:** every docs task → ask the agent to create/update both vi/en versions (`main` Vietnamese, `example/nestjs-training` English). Hermes verification adds a step: diff the two branches (must be empty apart from language) + scan the EN version for Vietnamese characters. GitLab only syncs the EN version, author = `hienduong-agility`, no trailer.
