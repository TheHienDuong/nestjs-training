## 📚 Theory

### 1. The five files generated by `nest new`

```
src/
├── main.ts                 # entry point — bootstraps the application
├── app.module.ts           # root module — where everything is declared and wired together
├── app.controller.ts       # controller — receives HTTP requests
├── app.service.ts          # service — contains business logic
└── app.controller.spec.ts  # unit test for the controller
```

The official documentation describes it exactly as follows:

| File                     | Role                                                       |
| ------------------------ | ---------------------------------------------------------- |
| `app.controller.ts`      | A basic controller with a single route                     |
| `app.controller.spec.ts` | Unit test for the controller                               |
| `app.module.ts`          | The application's root module                              |
| `app.service.ts`         | A basic service with a single method                       |
| `main.ts`                | Entry file — uses `NestFactory` to create the app instance |

Something worth noting right away: **the framework imposes layering on you from the very first file.** Express doesn't do this — with Express you get an empty `index.js` file and decide everything yourself. That freedom sounds nice, but the cost is that every Express project is organized differently, and newcomers have to relearn the structure from scratch each time.

> 📖 Source: [/first-steps](https://docs.nestjs.com/first-steps)

### 2. `main.ts` — the entry point

```ts
// src/main.ts
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  await app.listen(process.env.PORT ?? 3000);
}
void bootstrap();
```

Line by line:

- **`NestFactory.create(AppModule)`** — takes in the **root module** and returns an object satisfying the `INestApplication` interface. Internally, Nest scans the entire module tree starting from `AppModule`, reads the metadata on the decorators, instantiates all providers, and **wires up the dependencies** between them. This is the **IoC container** at work.
- **Why `async`?** Because the initialization process may involve asynchronous work: connecting to a database, reading config from an external source, a `useFactory` that returns a Promise. Nest must wait for all of that to finish before the application can accept its first request.
- **`app.listen(port)`** — opens the HTTP listener. Only at this point does the application actually start accepting requests.
- **`void bootstrap()`** — `void` tells TypeScript that we are intentionally not `await`-ing this Promise. See the explanation in [L00](../00-setup/README.md#a-small-but-notable-modification-in-src).

**One option worth knowing:** by default, if an error occurs during application initialization, the app exits with exit code `1`. If you want it to **throw** the error instead of exiting (for example, to handle it yourself in tests):

```ts
const app = await NestFactory.create(AppModule, { abortOnError: false });
```

> 📖 Source: [/first-steps](https://docs.nestjs.com/first-steps)

### 3. Platform-agnostic — why does Nest decouple from Express?

Nest is **not** an HTTP framework. It is an architectural layer **sitting on top of** an HTTP framework. Two platforms are supported out of the box:

| Platform           | Characteristics                                                                                                                            |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `platform-express` | Express — minimalist, battle-tested over many years, large community, many libraries. **The default**, no setup needed to enable it.       |
| `platform-fastify` | Fastify — high performance, low overhead, focused on speed. See [/techniques/performance](https://docs.nestjs.com/techniques/performance). |

Why it's designed this way: so that **your application logic does not depend on the HTTP framework**. Your controllers, services, and modules know nothing about Express. Switching to Fastify is, in principle, just swapping the adapter — not rewriting your business logic.

Normally you don't need to care about the platform. Only when you want to reach into the underlying platform's API do you need to declare the generic:

```ts
import { NestExpressApplication } from '@nestjs/platform-express';

const app = await NestFactory.create<NestExpressApplication>(AppModule);
// now you can call Express-specific methods, e.g. app.set('trust proxy', 1)
```

> 🧠 **This is exactly hexagonal architecture** at the framework level. Express/Fastify is the **adapter** for the "HTTP server" port; your application is the **core**, unaware of which adapter is being used. You've built this pattern by hand before in your Express projects — here, Nest builds it for you.

> 📖 Source: [/first-steps](https://docs.nestjs.com/first-steps) · [/fundamentals/platform-agnosticism](https://docs.nestjs.com/fundamentals/platform-agnosticism)

### 4. How to run the application

| Command                          | What it does                                                        | When to use it              |
| -------------------------------- | ------------------------------------------------------------------- | --------------------------- |
| `pnpm start`                     | Compiles then runs once                                             | Quick check                 |
| `pnpm start:dev`                 | `nest start --watch` — auto-recompiles and restarts on file changes | **Main dev loop**           |
| `pnpm start:debug`               | Same as above, with `--debug` to attach a debugger                  | Setting breakpoints         |
| `pnpm build` → `pnpm start:prod` | `nest build` outputs to `dist/`, then `node dist/main`              | Mirrors how production runs |

The docs mention a tip worth knowing: use the **SWC builder** for a much faster build (the docs cite up to ~20x):

```bash
pnpm start -- -b swc
```

SWC is a Rust-based compiler, much faster than `tsc`, but it **does not type-check** — it only transpiles code. This is a reasonable trade-off for the dev loop, since you still get type-checking from your IDE and from `pnpm build` in CI.

> 📖 Source: [/first-steps](https://docs.nestjs.com/first-steps) · [/recipes/swc](https://docs.nestjs.com/recipes/swc)

### 5. `app.module.ts` — the root module

```ts
@Module({
  imports: [], // other modules this module depends on
  controllers: [AppController], // controllers belonging to this module
  providers: [AppService], // providers (services, etc.) managed by the DI container
})
export class AppModule {}
```

`@Module` is just **metadata**. The `AppModule` class itself is empty. Nest reads this metadata at startup to know what to instantiate and what to inject where.

Details are covered in depth in L03 (Providers & DI) and L04 (Modules). For this lesson, it's enough to see that: **this is where you declare "what exists in the application"**, separate from where it's implemented.

### 6. Controller and Service — why split into two?

```ts
// app.controller.ts — handles HTTP only
@Controller()
export class AppController {
  constructor(private readonly appService: AppService) {}

  @Get()
  getHello(): string {
    return this.appService.getHello();
  }
}
```

```ts
// app.service.ts — handles business logic only
@Injectable()
export class AppService {
  getHello(): string {
    return 'Hello World!';
  }
}
```

For a function that just returns `'Hello World!'`, this separation looks pointless. But this is a **deliberate convention**, and the reason becomes apparent as the system grows:

- The **Controller** answers the question _"where does this HTTP request map to, where do the parameters come from, what status code is returned?"_
- The **Service** answers the question _"what does this business operation actually do?"_ — and it **knows nothing about HTTP**. As a result, the same service can be used by an HTTP controller, a CLI command, a message queue consumer, or a cron job.

`constructor(private readonly appService: AppService)` is **constructor injection**. You never call `new AppService()` anywhere — Nest sees the `AppService` type in the constructor, finds the corresponding provider, and injects it automatically. This is the single biggest difference from Express, and is the main topic of L03.

> 📖 Source: [/controllers](https://docs.nestjs.com/controllers) · [/providers](https://docs.nestjs.com/providers)

### 7. `app.controller.spec.ts` — testing built in from the start

```ts
const app: TestingModule = await Test.createTestingModule({
  controllers: [AppController],
  providers: [AppService],
}).compile();

appController = app.get<AppController>(AppController);
```

Notice: the test **also builds a DI container**, just a smaller one — containing only what the test needs. This is a direct consequence of using DI: since the controller receives its dependency through the constructor, you can swap the real `AppService` for a mock without changing a single line in the controller.

**This is the real answer to "what is DI for?"** — not to make code look "professional," but to make dependencies **replaceable from the outside**, and testing is the clearest use case for this. Details in L16.

> 📖 Source: [/fundamentals/unit-testing](https://docs.nestjs.com/fundamentals/unit-testing)

## 🔗 Connecting to prior knowledge

| Express                                                 | NestJS                                            | Where the difference lies                                                                                                                             |
| ------------------------------------------------------- | ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `const app = express()`                                 | `const app = await NestFactory.create(AppModule)` | Nest is **async** because it must instantiate the entire dependency tree; Express is synchronous because it manages nothing on your behalf            |
| `app.listen(3000)`                                      | `await app.listen(3000)`                          | Equivalent in meaning                                                                                                                                 |
| `app.get('/', handler)`                                 | `@Get()` inside `@Controller()`                   | Express: routes registered via a **function call** at runtime. Nest: routes declared via **metadata** on a class, which Nest reads and auto-registers |
| Organize folders yourself                               | `.module.ts` / `.controller.ts` / `.service.ts`   | Nest imposes layering → every Nest project looks alike, and newcomers can read it immediately                                                         |
| `const svc = require('./service')`                      | `constructor(private readonly svc: Service)`      | Express: you fetch the dependency yourself. Nest: the dependency is **delivered** to you (Inversion of Control)                                       |
| Switching Express → Fastify = rewriting the app         | Switching platform = swapping the adapter         | Nest decouples logic from the HTTP framework from the design stage onward                                                                             |
| Tests must `jest.mock('./service')` at the module level | `Test.createTestingModule({ providers: [mock] })` | Dependencies are swapped at the container level, not by hacking the module loader                                                                     |

**Something worth thinking about:** in your Express + hexagonal projects, "wiring" dependencies had to be done by hand at the entry point — manually creating a repository instance, passing it into a use case, passing the use case into a handler. `NestFactory.create(AppModule)` does **exactly the same thing**, but reads metadata from decorators to know what to wire to what. You already understand _why_ wiring is needed; here, only the _how_ changes.
